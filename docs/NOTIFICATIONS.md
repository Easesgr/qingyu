# 通知接入

第一次安装请先看[安装与接入教程](GETTING-STARTED.md)。下文对应设置侧栏的「消息」（通知）与「信箱」（邮箱）。

通知页把聊天客户端的新消息预览、未读变化、IMAP 新邮件、待办提醒和未处理的 Agent 审批请求放在一起。通知记录只保留在本次运行的内存中；退出轻屿后清空，不会保存聊天记录或上传通知内容。

## 岛内显示

新通知从原岛下方展开为独立的单行浮条，显示来源图标、简短标题与状态，保留原有时间、音乐与导航。微信等聊天通知在同一行显示来源、发送者和正文预览，较长的联系人或群名称会截断，为正文留出空间。长内容通过悬停提示查看；点击消息本身或“查看”都打开对应来源，关闭按钮只关闭当前提示。多个通知依次显示，打开的聊天通知会同时从轻屿浮条、队列与通知记录中移除，同一通知的延迟副本不会再次弹出。岛已展开时保留当前主控或详情，浮条依然位于面板外侧。靠近屏幕底部时自动调整位置留在屏幕内，动画遵循减少动态效果设置。

聊天和邮件按独立消息身份累计到队列，浮条中的 `+N` 表示后面还有 N 条。较早的消息不会因超过 8 条而被丢弃，每条轮到展示时都有完整阅读时间。待展示消息保留在本次运行的通知记录中；已经展示过的普通历史保留最近 50 条。系统先给出姓名、稍后补出正文时，会更新同一条消息，不增加队列数量。Dock 未读数是汇总信息，不能拆成不存在的单条正文。

普通通知、Agent 开始与完成提醒显示 15 秒，普通等待和中断提醒显示 20 秒。鼠标悬停或键盘焦点停留在浮条控件时暂停计时，离开后继续。作为参考，Material 2 的 [Snackbar 行为规范](https://m2.material.io/components/snackbars#behavior) 建议 4–10 秒；轻屿根据阅读需求采用更长的显示时间。

Agent 只在真实会话的开始、等待、审批、中断和完成事件到达时提示，显示具体对话名称与对应应用图标，各事件带有相应的图标动画，完成时显示本轮总用时。不会按固定间隔重复提示。审批请求明确显示“需要审批”，保留到用户点击或主动关闭；审批操作在对应 Agent 应用内进行。点击 Codex、Claude 等通知会直接打开对应的外部应用或窗口。Codex 优先使用对话链接；终端或编辑器内的 Agent 依据观察到的进程身份打开所属应用，能否选中准确标签取决于窗口识别信息与已有系统权限。

开始、普通等待、中断与完成提醒不加入通知记录；未处理的审批提醒保留在本次运行的通知记录中。Agent 页中的完成任务保留 1 分钟后自动移除。仅检测到进程存在不会触发任务完成通知。

开发版的岛内提示直接由应用绘制。macOS 系统通知依赖应用身份和系统授权；不具备通知身份的命令行开发版仍可在岛内显示提醒。

## QQ、微信与其他客户端

macOS 没有供普通应用使用的通用第三方通知订阅接口。轻屿通过辅助功能接口读取系统当前公开的通知预览，以及客户端在 Dock 中公开的未读标记。

| 系统提供的信息 | 轻屿的行为 |
| --- | --- |
| 可见且公开正文的系统通知 | 展示来源及系统提供的发送者、正文预览 |
| 系统只提供一段合并后的通知描述 | 保留系统原文，不猜测逗号分别属于发送者还是正文 |
| 仅有 Dock 未读标记变化 | 显示“有新未读消息”，无法补出发送者或正文 |
| macOS 因屏幕共享、镜像或专注模式而静音系统横幅 | 仍可能读到 Dock 未读数；需要先恢复系统通知展示才能采集预览 |
| 系统隐藏预览、客户端未发通知，且未读标记没有变化 | 无法保证发现该条消息 |

点击通知时，原系统通知仍存在且提供可用操作，轻屿可以调用原通知的打开动作。通知已经消失或系统未提供操作时，只能打开来源应用，不能保证定位到对应聊天。轻屿不会主动展开通知中心，也不会获取完整聊天记录。

客户端需启用系统通知和内容预览；轻屿不会绕过系统隐藏预览的设置。辅助功能授权不代表 QQ 或微信账号已经登录或完成账号授权。

在「设置 → 消息」中开启「接收通知」与「启用系统通知监测」，选择 QQ、微信等需要的来源，并按需开启「显示内容预览」。点击「打开辅助功能设置…」，按系统说明前往「系统设置 → 隐私与安全性 → 辅助功能」授权；macOS 12 对应「系统偏好设置 → 安全性与隐私 → 隐私 → 辅助功能」。轻屿不会在启动时自动弹出权限请求，无须输入 QQ 或微信的账号密码。设置页的权限提示来自同一后台采样器，授权变更后在后续采样中自动更新。

首次连接、重新启用和解锁后先建立当前状态基线，已有未读不会集中重放。系统稍后为同一通知补齐发送者或正文时，更新原通知；不同原生通知保留各自的身份。多条新消息按顺序加入待显示队列，已经打开的通知不会因延迟补齐重新出现。关闭来源或通知接入后停止采集；锁屏期间暂停。

临时无法连接 Dock 或通知中心时，保留各通道上一次成功采样的去重基线；恢复后继续识别新事件。撤销辅助功能权限或锁屏会清除基线，重新允许后先对齐当前状态，再接收新通知。通知记录仍只保留在本次运行中；授权持久性由 macOS 根据程序签名身份管理。

## 邮箱

在「设置 → 信箱」中添加账号并启用收信，完整步骤见[首次接入邮箱](GETTING-STARTED.md#5-接入邮箱)。邮箱通知沿用已有的 IMAP 接入，不依赖 Dock，也不需要辅助功能权限。启动时载入的历史邮件保持静默，后续新邮件进入通知页。

| 邮箱服务 | 接入方式 |
| --- | --- |
| QQ 邮箱 | 开启 IMAP，填写客户端授权码 |
| 163 / 126 | 开启 IMAP，填写客户端授权密码 |
| 腾讯企业邮 | 按企业策略启用 IMAP，填写客户端专用密码 |
| iCloud | Apple 账户的 App 专用密码 |
| Gmail | Google 账户的应用专用密码；受账号与组织策略限制 |
| 学校、单位等自定义邮箱 | IMAP over TLS，填写主机、端口及登录身份 |
| Outlook / Hotmail / Microsoft 365 云邮箱 | 需要 OAuth，当前尚未接入 |

凭据保存在系统钥匙串。通知预览沿用邮件验证码遮蔽规则，验证码请到邮件页面查看。

## 隐私和排查

通知来源和预览设置在「设置 → 消息」中管理。关闭预览后，列表与提醒使用通用文字。清空通知列表只清除轻屿的记录，不会将 QQ、微信或邮箱中的消息标记为已读。

收不到聊天提醒时，检查来源开关、辅助功能授权、客户端的系统通知和内容预览设置，以及是否确实新增了通知或 Dock 未读消息。收不到邮箱提醒时，检查邮箱页的连接状态、IMAP 开关和授权码。没有新事件时，列表为空属于正常状态；页面提供接入入口。

开发版可以执行 `target/debug/qingyu --notification-access-check`。它输出当前进程的 PID、父进程 PID / 应用标识、可执行文件路径、签名标识、签名验证状态、指定代码要求及 `accessibility_granted`，不打开窗口、申请权限或读取消息。已允许时退出码为 0，未允许时为 2。

`permission_scope=current_launch_context` 表示结果仅适用于这次命令启动；`running_gui_authorization=not_checked` 表示没有检查另一个已运行的轻屿窗口。macOS 可能把终端或 Codex 启动的命令归属到启动器，因此命令输出 `true` 不能证明从访达打开的 `/Applications/轻屿.app` 已获授权。父进程也不一定是 TCC 最终判定的责任进程，公开 API 无法读取完整归属链。

实际 GUI 的采样器会向统一系统日志的 `com.qingyu.macos` / `notification-access` 类别写入自身 PID、签名标识、指定代码要求与权限状态变化。日志不包含通知标题、发送者或正文。排查时先核对实际 GUI PID，再查看同 PID 的记录；签名验证成功只证明程序身份有效，不代表辅助功能已经允许。

如果辅助功能列表显示已允许，但实际轻屿仍提示无权限，先核对正在运行的应用路径。旧的 ad hoc 包按代码哈希识别，每次构建可能改变；旧授权不能自动迁移到新的证书签名。完成最后一次统一打包、将应用放到最终位置后，在系统辅助功能列表移除旧的轻屿条目，再添加该位置的轻屿并允许一次。后续包保留同一证书、应用标识与指定代码要求，才能保持稳定身份；开发版 `com.qingyu.macos.debug` 与安装版 `com.qingyu.macos` 分别管理授权。程序不会自动重置系统授权或修改权限数据库。

使用同一开发数据目录执行 `QINGYU_DATA_DIR="$PWD/.dev-data" target/debug/qingyu --notification-connection-check`，可检查已选 QQ、微信来源的实际采集通道。该命令先输出上述启动上下文，再最多等待 5 秒，输出启用状态、是否可用和识别到的应用数量，不输出发送者或消息正文。通道可用的退出码为 0，其余状态为 2；通道可用不代表已经实测收到某条消息，也不证明另一个 GUI 实例获授权。

预览通道的状态区分「尚未捕获预览」和「预览与未读监测中」。能读取通知中心的辅助功能根节点，只能证明连接可用；当前监测周期真正读到所选来源的正文后，才显示已捕获预览的状态。只收到 Dock 标记时依然使用通用未读提示。

需要检查真实预览时，执行：

```sh
QINGYU_DATA_DIR="$PWD/.dev-data" bash scripts/macos-dev-runner.sh target/debug/qingyu --notification-preview-check --notification-preview-seconds=5
```

诊断使用与应用相同的原生采集器，先输出上述启动上下文；时长限制为 1–60 秒，默认 5 秒，不打开通知中心、不请求权限、不发送消息。每次采样仅输出来源 bundle ID、节点类型、来源归属方式、解析路径、发送者／正文长度、候选数量和 AX 错误码，不输出应用通知的标题、发送者或正文，也不保留原生打开操作。最后的 `captured` 表示当前启动上下文在检查期间是否实际采集到正文；捕获时退出码为 0，否则为 2。`preview_accessible=true` 且窗口数为 0 表示系统没有向当前读取者公开通知窗口，不能据此认定客户端已发出可读取的通知。

## 接入边界

QQ 开放平台的机器人接口面向机器人收到的消息，不能直接用作现有个人账号全部会话的收件箱。第三方客户端桥接需要单独部署和维护，也会受到客户端版本与账号策略影响，本次通知接入不修改 QQ 或微信客户端。

系统通知的辅助功能结构也会随 macOS 版本变化。例如 [Sequoia 通知解析讨论](https://forum.latenightsw.com/t/parsing-notifications-in-macos-sequoia/5001) 记录了静态文本转为合并描述的变化。轻屿只接收能够明确归属到所选应用的预览，无法确认来源时跳过；短暂出现、被合并或未公开的通知可能遗漏。因此，来源、发送者、正文和会话打开能力以系统实际提供的内容为准；不会把未读标记伪装成已取得的聊天正文。
